# 项目协作协议（PROTOCOL）

> 项目：ai-pet · 建立：2026-11-03 · 基线：`main` · 集成：`team/integration`
>
> 本文件是项目的最高协作规则。**对话里说过的不算数，写进公告栏 / 任务书 / 仲裁记录才算发生。**
> 所有状态变更只通过 `node .team/tools/team.mjs`，手改 `.team/` 状态会被 `doctor` 记为不一致。

## 0. 一句话

管理层拆任务、派子会话、裁决、验收；执行者只认领一个任务、只写自己的写集；**交接走公告栏，冲突走仲裁，集成走门禁**。

## 1. 角色与权限

| 角色 | 谁 | 能做 | 不能做 |
|---|---|---|---|
| 用户 | 人 | 改范围/优先级/预算；批准结构变更与不可逆操作 | — |
| 管理层（仲裁者） | 当前会话或专门开的顶层会话；同时只有一个 | 需求深拆、写任务书、`dispatch` 子会话、驳回、验收、CR 裁决、记公告 | 不写业务代码；不替执行者改产物 |
| 架构师（管理层子角色） | 按需 | 契约、模块边界、ADR、结构性 CR | 不绕过仲裁改任务写集 |
| 执行者 | 每任务一个 `subagent` 会话 | 只写任务写集；`claim`/`submit`/`report` | 不改 `.team/`；不改别人任务；不扩范围 |
| 集成者 | 管理层兼任或独立会话 | `integrate`、跑门禁、冲突回滚 | 不放宽门禁；不静默解冲突 |

子会话规则：子会话不能再开子会话（`maxDepth=1`）；需要更高并行由管理层继续扇出；同时活跃执行者建议 ≤ 6。

## 2. 公告栏

`.team/BULLETIN.md` 是唯一人读交接渠道，由 CLI 生成，**禁止手改**。

- 一行一任务；任务 id 稳定；只更新自己那行；不删行。
- 证据列必须能复核：提交号、文件路径、命令、退出码；空证据 = 未完成。
- `## 公告 / 通知` 用于冻结、交接、变更通知；只追加。
- 状态真相在 `.team/local/board.json`；公告栏与真相不一致时先跑 `doctor --fix`。

## 3. 状态机

```text
待认领 → 进行中 → 待验收 → 已集成 → 已完成
            ↘ 驳回 → 进行中        ↘ 关闭（不做 / 无解，必须写原因）
            ↘ 阻塞 / 等人 → 进行中
            ↘ 待仲裁 → 进行中 / 驳回 / 关闭
```

| 状态 | 含义 | 谁推进 |
|---|---|---|
| 待认领 | 任务书已写、可能已 dispatch | 执行者 `claim` |
| 进行中 | 持有租约、在写集内工作 | 执行者 `submit` |
| 待验收 | 已提交、有证据 | 管理层 `integrate` 或 `reject` |
| 待仲裁 | 冲突/争议未裁决 | 管理层 `arbitrate --decide` |
| 已集成 | 已进集成分支且门禁通过 | 管理层 `accept` |
| 已完成 | 验收通过，写进台账 | — |
| 关闭 | 不做 / 无解 | 必须写原因 |

## 4. 写集与租约（防止同文件冲突）

1. 任务书必须声明 `write`（写集 glob）。执行者**只准改写集内文件**，`submit` 会用分支 diff 逐文件核对。
2. 任务分支**禁止改 `.team/**`**；控制面由管理层在基线提交。
3. 写集两两重叠的任务**不得并行**；顺序 = 依赖 → 优先级 → 认领时间（FIFO）。
4. 保护文件（lockfile、包清单、入口注册、DI、schema、迁移、生成物）默认归集成者；任务要改必须 CR 或短租约。
5. 租约：`claim` 时按写集加租约，TTL 默认 30 分钟；干活期间 `renew`；过期可被 `claim --takeover` 回收（记事件）。
6. 一任务一 worktree：`<仓库父目录>/<仓库名>.team-worktrees/T-00x`，分支 `task/T-00x`；集成分支独立工作树。
7. 重依赖目录（`node_modules`/`.venv`）可用 `config.linkDirs` 以链接共享到任务工作树；**任务工作树内禁止安装/升级依赖**，改依赖必须走 CR 或由集成者在控制面处理。
8. 确需并行改同一文件：管理层 `dispatch --override-overlap --reason "..."`，必须落 ARB，合并串行化；这是例外而非常态。

## 5. 仲裁条款（裁决必须引用条款号）

1. **接口契约 > 实现细节**：契约拥有者定签名；消费者只改自己一侧并加 adapter。
2. **租约持有者 > 非持有者**：租约内他人禁写；TTL 到期且无法证明 owner 存活才可回收。
3. **写集重叠不得并行**：顺序 = 依赖 → 优先级 → 认领时间。
4. **保护文件归集成者**：任务需改必须 CR / 短租约，禁止"顺手改一下"。
5. **集成冲突默认"后到者改"**：保持先合并者稳定；除非后到者方案已被 ADR 采纳。
   后到者在自己任务工作树里 `git rebase team/integration`，解决冲突后 `reopen`（若已关闭）+ `submit`；
   `submit` 在已包含集成分支时以集成分支为校验基线，只核对本任务写集。

6. **执行者不得自行扩写集、改契约、改别人的任务行**；`--override` 必须留 ARB 与原因。
7. **无法判定 → 升级用户**：范围、优先级、不可逆操作、第三方安装，状态 `等人`，不做静默取舍。

仲裁记录：`.team/ARBITRATIONS/ARB-###.md`，必须含触发、证据、适用条款、候选方案、决定、执行动作、复议条件。
未 `--decide` 前保持 `待仲裁`，双方不得继续写重叠路径。

## 6. 需求变更（CR）

新需求先 `cr new` → `cr impact` → 管理层定级 → `cr apply` → 只重排受影响任务 → 记 ADR。

| 级别 | 适用 | 做法 |
|---|---|---|
| additive | 新模块/新能力，接口只增不改 | 新增任务；现有任务零改动 |
| modify | 改现有模块行为，写集不变或缩小 | 任务书追加 addendum，重跑该任务门禁 |
| structural | 拆模块/换接口/换技术 | 必须 ADR + 冻结集成 + 契约 v2 + adapter + 迁移任务 |

最小改动五条：优先新增文件而非改公共文件；接口向后兼容；单任务写集尽量小；重排只碰受影响任务；结构变更必须有过渡层和回滚点。
任何 CR 先 `git tag pre-CR-###` 留回滚点。

## 7. 证据与验收

- `submit` 必须带：测试命令、退出码、HEAD、分支 diff 统计；工作树必须干净。
- 需要人工点界面/重启才能验的项，`submit --needs-human`；`accept` 必须 `--human-ok`，执行者和管理层都不许自勾。
- 门禁失败不许改验收命令绕过；改任务书验收标准必须走 CR 并留记录。

## 8. 会话规则

- 执行会话开场只读：`PROTOCOL.md`、`BULLETIN.md`、`TASKS/T-00x.md`、会话简报。
- 只在任务 worktree 里运行 `claim` / `submit`；在错误目录直接拒绝。
- 完成后回报：改了什么、证据、没做完的部分、下一步。不写"应该没问题"。
- 任务结束/被驳回后，管理层保留子会话 id，用 `send_message` 继续，不重开。

## 9. 常用命令

```text
team.mjs init [--gate "pnpm test"]
team.mjs status / bulletin / doctor
team.mjs task add --title ... --module ... --write "src/**" --verify "node --test"
team.mjs dispatch --id T-001
team.mjs link --id T-001 --session <子会话id>
team.mjs claim --id T-001 --token <token>
team.mjs submit --id T-001 --token <token>
team.mjs integrate --id T-001
team.mjs accept --id T-001 [--human-ok]
team.mjs reject --id T-001 --reason "..."
team.mjs reopen --id T-001 --reason "..."
team.mjs cr new / cr impact / cr apply
team.mjs arbitrate --task T-001 --decide --decision "..."
```

## 10. 反模式（见到就停）

- 执行者自己验收自己；管理层替执行者写代码。
- 只在对话里汇报、不落公告栏；"理论上可以"当证据。
- 一个任务多个认领者；绕过 `claim` 直接改文件。
- 写集重叠还硬并行；冲突后静默覆盖对方。
- 需求一变就重写架构；结构变更没有 ADR / 回滚点。
- 公告栏和任务书两套状态打架（先修任务书/状态，再重渲染公告栏）。
