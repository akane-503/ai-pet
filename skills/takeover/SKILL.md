# 接手交接任务

## 增量返回原会话

参数以 --incremental 开头（兼容旧版增量）（例如 `$takeover --incremental 修复桌宠`）时，先去掉这个模式词，再按下面的规则用剩余任务名找文件。当前会话已有上下文：只吸收交接文件里新增的改动、验证、决策和待办，与本会话已知信息去重；进度以实际 Git 和文件为准。新旧结论冲突先指出并核对，不覆盖已有用户改动，不重复完成的工作。无需重讲完整历史，简短说明新增信息和下一步，再继续。

## 接手步骤

1. 找交接文件。参数通常只是一句任务名（桌宠发的就是 `$takeover <任务名>`），不要指望它带路径：
   - 参数是现存的文件或路径（含旧版 `[项目_会话] 路径` 里的路径）就直接读它；
   - 否则当任务名找 `HANDOFF*.md`：先在当前目录找（交接文件跟着会话工作区走，可能在 git 项目根的子目录里），没有再查 git 项目根（`git rev-parse --show-toplevel`，不是仓库就只有当前目录）。先挑文件名或首行 `# HANDOFF —` 标题含这个任务名的，没有再取 mtime 最新的；`~/.handoff/latest.txt` 最后一行若落在本项目也算候选；
   - 都对不上、或几个候选互相矛盾时问用户，别猜。
2. **核对，不要盲信**：用 `git log -5`、`git status`、`git diff <锚点>` 对比"代码锚点"和"改动清单"，列出不一致之处。`[未验证]` 项视为未完成。
3. 向用户简短复述：目标、用户原话里的约束、你要执行的下一步，以及核对发现的不一致。
4. 有疑问先查"原始对话"路径（jsonl 用 grep 搜关键词，别整份读入）；仍不清楚再问用户。
5. 从"下一步"第 1 项开始。每到阶段节点更新 HANDOFF.md（来源工具改成你自己，保留旧的"已知坑"）。

## 实测补充

- 优先使用用户明确给出的交接文件路径；交接文件目录与当前工作目录不同时，记录两者，勿擅自初始化或扫描整个家目录。
- 无 Git 时核对明确列出的文件、修改时间与必要的哈希，不运行依赖不存在锚点的 diff；Git 有差异时保留用户改动，先解释证据。
- 分开验证“文件存在”“链接解析且消费端可读”“本次技能清单包含”“真实调用完成”。手动读入 SKILL.md 并执行流程须如实注明，不算已验证自动发现。
- 路径需注明 Windows/WSL；仅凭 WSL 的软链接不能证明 Windows 工具加载成功。修改技能只编辑指定唯一源，受管副本通过已授权的管理器分发。
- 原始对话只按明确会话 ID 和任务关键词局部检索；不能把全局最新对话当成本任务，也不向第三方发送凭据或无关聊天。
- 已授权的安装方式直接沿用。发现新权限、外部行动或关键歧义才询问；实际失败、超时与未完成步骤写回交接文件。
- 如果存在 state/requests.md、handoff.md、progress.md、decisions.md、evidence.md，按适用任务规则读取并校验；单个 HANDOFF.md 不等于正式 state/ 已初始化，不绕过写入者接管确认。
